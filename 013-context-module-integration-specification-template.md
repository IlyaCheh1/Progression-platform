# Техническое задание на описание контекстного модуля

## 1. Назначение документа

Этот документ определяет обязательную структуру ТЗ для подключения нового вида
деятельности к Progression Platform.

Заполненное ТЗ должно одновременно давать:

- понятное описание деятельности организации;
- модель текущих и целевых бизнес-процессов;
- границу между бизнес-модулем и ядром платформы;
- перечень функциональных доработок;
- каталог событий для интеграции;
- правила прогрессии и стартовый RPG-контент;
- требования к данным, безопасности и эксплуатации;
- план внедрения и проверяемые критерии приёмки.

Документ применяется для любых контекстов: образования, спорта, фитнеса,
сообществ, корпоративного обучения, мероприятий, маркетплейсов и других видов
деятельности.

# 2. Правила заполнения

## 2.1. Обязательность

Все разделы ТЗ обязательны.

Если раздел неприменим, автор указывает:

```text
Неприменимо.
Причина: <проверяемое объяснение>.
Подтверждено: <роль или владелец решения>.
```

Пустой раздел не считается ответом.

## 2.2. Нормативные формулировки

- **ДОЛЖЕН** — обязательное требование;
- **НЕ ДОЛЖЕН** — запрещённое решение;
- **СЛЕДУЕТ** — рекомендуемое решение, отклонение требует объяснения;
- **МОЖЕТ** — допустимый вариант.

Фразы «удобно», «быстро», «интуитивно», «при необходимости» и аналогичные
формулировки не считаются требованиями без измеримого критерия.

## 2.3. Разделение фактов и решений

Каждое существенное утверждение помечается одной категорией:

| Категория | Значение |
|---|---|
| `SOURCE` | подтверждено исходным документом или системой |
| `OBSERVED` | установлено при анализе текущего процесса |
| `DECISION` | согласованное продуктовое или архитектурное решение |
| `ASSUMPTION` | временное предположение, требующее проверки |
| `OPEN` | незакрытый вопрос, блокирующий или неблокирующий |

## 2.4. Идентификаторы требований

Каждое функциональное и нефункциональное требование получает стабильный ID:

```text
<КОД-МОДУЛЯ>-<ВОЗМОЖНОСТЬ>-<НОМЕР>
```

Примеры:

- `FIT-BOOK-001`;
- `EDU-COURSE-014`;
- `COMM-NFR-006`.

ID не меняется при редактуре текста требования.

Приложить схему не ниже этого уровня:

```text
Пользователь или сотрудник

    → авторитетный агрегат модуля
    → транзакционный outbox
    → платформенные события
    → Reward / Quest / Achievement
    → owning Engine
    → проекция
    → интерфейс пользователя
```

# 32. Запрещённые архитектурные решения

Модуль НЕ ДОЛЖЕН:

- записывать данные в базы Engine;
- рассчитывать Level самостоятельно;
- выдавать XP напрямую без Reward policy;
- хранить Level в CRM;
- считать платёж игровой валютой;
- смешивать User, Character, клиента, плательщика и участника;
- использовать имя, телефон или e-mail как aggregate ID;
- принимать клиентское событие `completed` без серверной проверки;
- иметь двух writers одного состояния;
- редактировать опубликованное событие;
- предполагать exactly-once delivery;
- использовать float в авторитетной игровой арифметике;
- публиковать лишние персональные данные;
- активировать неизвестный Reward Component или Talent Effect;
- создавать невалидируемые циклы Reward → Quest → Reward;
- переносить доменную логику в универсальный Engine;
- делать публичной прогрессию несовершеннолетнего по умолчанию;
- импортировать исторические данные без provenance и reconciliation.
